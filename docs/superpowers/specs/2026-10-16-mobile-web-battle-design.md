# 모바일웹 가족 대전 설계

날짜: 2026-10-16. 상태: **설계·계획 승인 후 구현/검증·리뷰 수정·배포 완료**. 운영 종단 대전은 참가자/카드 준비 이후 검증. 아래 검토 대기 표현은 작성 당시 기록이며 현재 상태는 STATUS.md 우선. 구현 계획: ../plans/2026-10-16-mobile-web-battle-plan.md.

## 1. 목적과 범위

두 사람이 휴대폰 한 대를 번갈아 사용하여 실제 카드게임의 전투 전략과 진행 속도를 테스트한다. 기존 React/Worker/D1 어드민을 재사용하며, 같은 사이트에 게임 화면을 추가한다. Android 네이티브 개발은 보류한다.

포함: 진영 선택, 20장 덱 고정, 턴제 전투, 수비자 피해 선택, 효과 6종, 승패, 재접속, 공개 전투 기록.

제외: 실시간 원격 대전, 매칭, 랭킹, 별도 앱 패키징, 오프라인 전투, AI 상담, 검증되지 않은 승률 점수, 유료 서비스 가입.

무료 한도 내 가족 테스트이며 무제한 사용을 보장하지 않는다. 비동기 요청/응답으로 동작하며 지속 polling/WebSocket/새 서비스는 도입하지 않는다.

## 2. 확정 규칙과 이번 문서의 제안 구분

모바일웹 방향과 직전 대화의 규칙 표, 처음부터 플레이어별 개별 계정을 사용한다는 방침은 승인됐다. 상세 근거는 game-rules-v1-proposal.md 및 game-rules-audit.md에 보존한다. 이 문서의 구체적인 기기 인증 흐름, 초기 배치, 효과 적용 대상, API/DB 설계는 구현을 위한 **검토 대상 제안**이다. 문서 승인 전 구현하지 않는다.

### 계정 방식: 플레이어별 개별 계정 확정

사용자가 처음부터 각자 계정을 유지한다고 명시했다. **서로 다른 두 실제 계정이 모두 로그인해야 시작**하며, 한 계정 두 자리·게스트 계정·표시명만으로 상대를 등록하는 방식은 허용하지 않는다. 한 계정 두 자리 제안은 폐기한다. 일반 사용자와 관리자 모두 플레이어가 될 수 있으나 관리자 권한으로 상대 인증을 대신하지 못한다. 게임 결과는 두 계정 ID와 각 진영에 연결하며 랭킹/승률 대시보드는 별도 범위다.

기기 인증 제안: 플레이어 1 로그인·대기방 생성 → 플레이어 2가 기존 로그인 API로 자기 계정 로그인·참가 → 두 계정이 확인된 대전 전용 기기 권한으로 교대. 브라우저의 일반 로그인 쿠키는 두 번째 계정으로 바뀌지만, 대전 전용 권한은 두 참가자 ID에 묶여 유지한다. 두 번째 로그인 실패나 자기 계정 중복 참가로는 두 번째 권한을 얻지 못한다. 대기방 ID만 알아서는 참가 불가하며, 방 생성 때 발급된 해당 기기 토큰과 두 번째 계정 로그인이 모두 필요하다.

대전 전용 권한은 무작위 opaque 토큰을 HttpOnly·SameSite Strict·HTTPS Secure 쿠키로 보관하고 서버에는 해시만 저장한다. 일반 계정/관리자 인증에 사용할 수 없다. 최대 7일 만료, 명시적 로그아웃 시 해제. 생성 후 첫 계정만 인증된 토큰은 참가자 1에만, 두 번째 참가 성공 후에는 그 대전의 두 참가자에게만 권한을 가진다. 계정 정지·일반 세션 만료/취소도 검증하며, 권한 복구 시 해당 참가자 각각 재로그인이 필요하다. 비밀번호/세션 원문은 JS 저장소·URL·게임 데이터·로그에 저장하지 않는다.

인증은 게임 시작 때 각자 한 번으로 하고 매 턴 비밀번호를 요구하지 않는다. 한 기기 공유자는 양쪽 행동을 실행할 수 있다. 계정 연결은 검증하지만 실제로 기기를 넘겨받은 사람이 누구인지는 인증하지 않는다. 온라인 부정행위 방지 제품으로 설명하지 않는다.

## 3. 사용자 흐름

1. 플레이어 1 로그인 후 ‘대전’에서 자기 진영으로 대기방 생성. 같은 기기에서 플레이어 2가 자기 계정으로 로그인한 뒤 자기 진영을 선택해 참가. 같은 계정 재참가는 거부. 같은 진영 대전 허용, 카드 인스턴스는 자리별로 독립. 로그인에 따라 Workspace가 교체되어도 대기방 경로와 서버 기기 권한으로 참가 화면을 복원.
2. 두 번째 계정 참가 시 서버가 양 진영의 승인·활성·미보관 카드 준비 조건을 한 DB 스냅샷에서 재검증. 엑조디아 정확히 5장, 비엑조디아 15장 이상이어야 한다. 대기방 생성 시에는 덱을 선정하지 않으며 참가·덱 생성·시작은 한 원자적 전환으로 처리.
3. 자리별 엑조디아 5장 + 무작위 비엑조디아 15장 선정 후 총 20장 전체를 셔플. 선공도 서버 무작위 선정. 클라이언트가 덱/seed를 지정하지 못함.
4. 각자 딱 1장 최초 공개. 일반 카드는 공격 칸에 배치, 엑조디아면 대기 칸으로 보내고 추가 공개 없이 시작. 최초 공개는 정규 턴을 소비하지 않는다.
5. 행동 주체 안내 후 오픈 또는 공격 선택. 수비 선택이 필요하면 ‘상대에게 기기를 넘겨주세요’ 화면을 거침.
6. 서버 상태를 표시하고 다음 턴으로 전환. 승패 시 결과와 다시 대전 버튼 표시. 새로고침은 같은 세션을 복원하며 새 덱을 만들지 않는다.

## 4. 행동과 승패

### 정규 오픈

- 덱이 비어 있으면 불가. 빈 칸이 하나면 자동 배치, 둘이면 오픈 전에 공격/방어 칸 선택. 가득 찬 경우 자리 선택 없음.
- 일반 카드는 선택한 빈 칸으로 이동. 전장이 찼으면 공개하지 않고 버림 더미로 이동하고 복귀 불가. UI와 공개 로그에는 버림 수만 표시.
- 엑조디아는 대기 칸으로 이동하고 그 턴 종료. 다섯 번째면 즉시 승리.
- 정규 오픈을 선택한 턴에는 일반·특수 공격 모두 불가.

### 공격과 수비

- 일반 공격 또는 자기 특수 공격을 선택. 공격자가 방어 칸 카드라면 공격/방어 자리 교환을 해당 공격 행동의 일부로 수행. 교환 후 방어 칸으로 패시브를 판정.
- 피해 공격은 대상 선택 대기 상태를 저장. 수비자가 자기 공격/방어 칸 중 살아 있는 카드 하나를 선택. 하나만 있으면 자동 선택. 선택 전에는 피해·사망·턴 전환 없음.
- 공격할 상대 카드가 없으면 피해 공격 불가. 자기 회복 특수 공격은 자기 HP가 감소해 있으면 상대 전장과 무관하게 가능.
- 특수 공격은 카드 인스턴스별 게임당 1회. 자리 이동·보충·재접속으로 초기화 안 됨. 서버가 불법 요청을 실행 전에 거부하면 턴/사용권/자리 모두 그대로이며, 요청 거부를 실패 효과 발동으로 취급하지 않는다.
- 반격·공격자 HP 자동 소비·초과 피해 이월 없음. 대기 엑조디아와 비공개 덱/버림은 공격 대상 아님.

### 사망 보충과 판정

- HP가 0인 카드를 사망 영역으로 보내고, 해당 칸마다 덱에서 정확히 1장 무료 보충. 덱이 비면 보충하지 않음.
- 일반 카드는 사망한 칸에, 엑조디아는 대기 칸에 두고 원래 칸은 비워둠. 추가 무료 공개·추가 공격·다음 턴 강제 스킵 없음.
- 사망 → 1장 보충 → 엑조디아 5장 승리 확인 → 전장 및 남은 덱에 전투 가능한 일반 카드가 전혀 없는 플레이어 패배 순으로 판정. 버림/사망 카드는 전투 가능 자원으로 세지 않음.
- 공격 처리 완료 후 턴을 바꿈. 새 카드의 즉시 사용은 다음 합법적인 자기 공격 기회부터라는 의미이며 상대 턴 난입 공격 없음.
- 합법 행동이 없을 때만 자동 패스. 각 자동 패스 전에 승패를 검사. 사용자 선택에 의한 패스·단독 자리 교환·자동 무승부·시간/턴 제한은 추가하지 않음.
- 유한한 회복 횟수와 피해 최소 1은 무한 회복을 방지한다. 사용자가 반복 행동을 선택하는 모든 상황의 유한 종료까지 보장한다고 주장하지 않음.

## 5. 효과 6종의 첫 버전 정의

아래 적용 대상·순서는 이번 문서의 상세 제안이다. 기존 편집기의 설명도 함께 갱신해 화면과 판정이 일치하게 한다. 기존 카드 레코드 자체를 일괄 수정/재승인하지 않으며 신규 게임의 rules_version으로 변경을 구분한다.

| 코드 | 발동과 처리 |
| --- | --- |
| fury | 방어 칸에 있을 때 아군 공격 칸 카드의 피해 공격 기본 공격력 ×1.1. 일반/강타/관통에 적용 |
| armor | 방어 칸에 있을 때 자기 자신이 받는 일반 공격만 ×0.9. 강타에는 적용하지 않으며 관통은 방어형 효과를 무시 |
| regeneration | 방어 칸에서 자기 턴 시작 시 자기 최대 HP의 5% 회복. 게임당 최대 3회, 실제 회복 때만 소비, 최대 HP 제한 |
| power_strike | 일반 공격 대신 공격자의 기본 공격력 ×1.5 피해. 공격 보정은 적용 |
| heal | 일반 공격 대신 공격자 자신 최대 HP의 25% 회복. 최대 HP 제한, 게임당 1회. 피해 대상 선택 없음 |
| pierce | 일반 공격 대신 기본 공격 피해. 공격 보정 적용, 방어형 패시브 무시 |

피해는 기본 공격력 → 특수 공격 배율 → 공격형 보정 → 적용 가능한 방어형 보정 → 소수점 버림 → 최소 1 → HP 차감. 배율은 정수 비율 연산으로 구현하여 부동소수점 경계 오차를 피한다. 회복은 소수점 버림 후 최대 HP까지, 최소 피해 1을 회복에 적용하지 않는다. 특수/패시브 사용 횟수는 카드 인스턴스에 귀속.

## 6. 서버 구조와 저장

- 순수 전투 엔진: 상태/행동을 검증하고 새 상태와 공개 이벤트를 반환. 네트워크·DB·DOM과 분리. 덱 생성의 난수는 서버에서만 주입하고 생성 결과 저장.
- Worker 게임 라우트: 기존 인증·동일 출처 검사를 재사용. 두 참가자만 자기 게임 조회 가능. 행동은 해당 게임의 기기 권한과 현재 단계/참가자 자리로 검증. 클라이언트가 보내는 user_id/actor_seat만으로 신원을 신뢰하지 않음. 관리자라도 다른 계정 게임 조회/참가를 대행할 수 없음.
- D1 신규 테이블만 추가. 기존 카드/계정/이미지는 삭제하지 않음.
- games: id, creator_user_id, rules_version, status(waiting/active/finished), version, turn_number, 전체 상태 JSON, 생성/수정 시각. active부터 40장 카드 스냅샷과 덱 순서·HP·횟수·전장·선공·대기 공격·승패를 포함. 이미지 바이트와 전체 이벤트 이력은 JSON에 넣지 않음.
- game_members: game_id, seat, user_id, faction_id. (game_id,seat), (game_id,user_id) 유일 제약과 기존 users/factions FK로 정확히 두 개의 서로 다른 실제 계정을 보장. 결과는 사용자별 목록에서 조회 가능.
- game_devices: token_hash, game_id, 인증된 두 참가자의 session token_hash 참조, expires_at. 생성 단계에는 첫 계정 권한만, 참가 성공과 동시에 두 계정 권한 부여. 두 인증 세션의 취소/만료/정지 여부를 검사. 대전 전용 쿠키는 해당 게임 경로에 제한하고 기존 일반 로그인·로그아웃과 역할을 구분. 로그아웃은 현재 기기의 대전 권한도 해제하도록 연결.
- game_actions: game_id, request_id, applied_version, 공개 이벤트 JSON. (game_id,request_id) 및 (game_id,applied_version) 유일 제약. 사용자 제공 원문/비밀번호는 저장하지 않음. 공개 로그에 덱 순서·비공개 버림의 카드 정보 금지.
- game_images: game_id,image_key. uploads FK로 사진 참조를 보호하고, 두 참가자는 승인 해제/카드 이미지 변경 후에도 당시 사진을 조회 가능. 기존 이미지 삭제 API에 게임 참조 차단을 추가. 게임 목록/로그에는 바이트를 포함하지 않음. 이미지 API는 현재 일반 로그인 계정의 참가자 여부를 검증하며 다른 계정 사진 접근을 허용하지 않음.
- 상태 갱신은 version CAS와 행동 기록을 원자적 D1 batch로 저장. CAS 실패 시 이벤트 기록도 없어야 한다. 두 번 탭·동시 탭에서 하나만 적용.
- 시작 시 단일 쿼리로 양 진영 풀을 읽고 승인된 수치/효과/버전을 고정. 이후 카드 변경은 진행 게임에 영향 없음. 사진 참조 보호까지 성공해야 게임 생성 성공.
- 한 세션 상태는 256 KiB 이하, 요청은 작은 식별자/행동만 허용. 로그와 목록은 최대 50개씩 페이지 조회. 무기한 자동 polling과 자동 삭제는 없음.

| API | 책임 |
| --- | --- |
| GET /api/games | 현재 로그인 계정이 참가한 게임 목록, 페이지당 최대 50개 |
| POST /api/games | 첫 참가자의 진영과 request_id로 대기방 생성, 첫 계정의 대전 기기 권한 발급. 생성 재시도도 중복 방지 |
| POST /api/games/:id/join | 두 번째 실제 계정 로그인 및 기존 대기방 기기 토큰 검증. 두 번째 진영·request_id로 참가하고 원자적으로 대전 시작 |
| POST /api/games/:id/device-authorizations | 원래 참가자 계정의 재로그인으로 만료/로그아웃 후 기기 권한 복구. 두 계정 모두 검증되기 전 행동 불가 |
| GET /api/games/:id | 공개 상태·전장·대기·덱/버림/사망 수·현재 행동 주체·합법 행동 |
| POST /api/games/:id/actions | request_id, expected_version, actor_seat, 행동/선택 식별자. 서버가 현재 단계/자리 검증 |
| GET /api/games/:id/events | 비공개 정보가 제거된 공개 이벤트, 최대 50개 |

게임 생성의 request_id는 생성 계정별 유일하게 저장. 같은 ID 재시도에는 기존 게임 반환. 참가 재시도도 동일한 두 번째 계정·request_id면 재추첨 없이 기존 시작 상태 반환. 다른 세 번째 계정/같은 계정 중복 참가/이미 찬 방 참가는 거부. 행동 중복에는 재적용하지 않고 현재 공개 상태와 최초 적용 버전을 반환. 409 버전 충돌이면 화면을 새 상태로 교체하고 사용자가 다시 선택. 수비자 선택 대기 상태도 새로고침 시 복원.

전송 중 실패하면 서버 적용 여부를 모르는 상태로 표시하고 조회/같은 request_id 재시도만 허용. 새로운 ID로 자동 재전송하지 않음. 불법 행동 400, 미인증 401, 다른 소유자 404, 버전/단계 충돌 409. 내부 상태 JSON을 응답에 그대로 serialize하지 않고 별도 공개 view 변환기를 사용.

## 8. 모바일 UI

- 기존 어드민 보존, 게임용 터치 화면을 분리. 첫 계정이 대기방 생성 후 두 번째 계정으로 전환하는 전용 안내 제공. 어드민은 항상 현재 일반 로그인 계정 권한만 사용하며, 상대 계정의 제작/관리 권한으로 전환할 수 없음.
- 세로 화면: 상대 전장/대기 → 턴/행동 주체 → 내 전장/대기 → 하단 행동 버튼. 작은 화면에서는 카드 상세를 누르면 확대.
- 단계별로 가능한 버튼만 표시하고 요청 중 중복 입력 차단. 최종 합법성은 서버 검증.
- 피해 대상 선택 때 두 카드의 현재 HP와 예상 피해를 보여주되 서버가 계산한 값 사용. 교환 전후 패시브 변화를 공격 확인 화면에 표시.
- 교대 안내는 편의 기능이며 개인정보/부정행위 보안 경계가 아님. 덱 순서·비공개 카드 이름은 화면/응답/로그 어디에도 보내지 않음.
- 새로고침 복원, 오류 재시도, 진영 준비 부족 이유, 종료 결과를 명시. 홈 화면 설치·서비스워커는 후속이며 첫 버전 필수 아님.

## 9. 검증과 완료 기준

- 엔진: 20장/엑조디아5 고정, 초기 엑조디아, 양 빈 칸, 가득 찬 오픈, 교환/패시브, 수비 선택, 최소 피해·반올림, 특수1회, 재생3회, 사망 보충 엑조디아, 엑조디아와 전투 패배 우선순위, 덱 소진/자동패스.
- API: 미인증/비참가자·관리자 우회 거부, 두 번째 로그인 실패·동일 계정 재참가·세 번째 계정 참가 차단, 첫 계정 권한만으로 두 번째 행동 차단, 대전 토큰으로 어드민 접근 불가, 세션 만료/로그아웃 후 복구, 비공개 덱/버림 누출 방지, 동일 request_id/동시 행동/오래된 version, 생성/참가 재시도, 수비 대기 복원, 도중 카드/이미지 변경과 보호, 지원하지 않는 효과 거부.
- 브라우저: 두 실제 계정으로 순차 로그인·진영 선택 후 모바일 한 기기 교대 대전, 계정 전환 뒤 대기방 복원, 각 계정에서 동일 결과 조회, 피해 선택 교대, 새로고침 복원, 로그아웃/재인증, 승패, 네트워크 응답 유실 재시도, 어드민 기존 제작·승인 회귀.
- 기존 verify·전체 브라우저 테스트 통과 후 운영 마이그레이션/배포. 운영 확인은 별도 기록. 사용자 카드/계정을 검증 목적으로 수정하거나 대량 테스트 데이터를 운영에 남기지 않음.
- 배포 성공과 실제 대전 성공, 실제 대전 성공과 밸런스 검증을 각각 구분. 첫 버전으로 승률이나 재미를 검증했다고 주장하지 않음.

## 10. 문서 검토에서 확인할 항목

1. 각자 계정 사용은 확정. 한 기기에서 순차 로그인한 뒤 게임 전용 권한으로 교대하고, 로그아웃 시 권한을 해제하는 구체적 흐름을 검토한다.
2. 초기 일반 카드 공격 칸 고정 및 초기 엑조디아 추가 공개 없음이 의도에 맞는가?
3. 효과 표의 대상·수치·일반/특수 적용 범위와 서버 세션/API 설계를 승인하는가?

설계 승인 후 구현 계획을 작성했다. 실행 방식은 기존 native 선택을 유지한다. 작성된 계획의 사용자 검토 전에는 제품 코드·DB 마이그레이션·운영 배포를 변경하지 않는다.
